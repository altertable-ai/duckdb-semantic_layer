# semantic_layer

[![CI](https://github.com/altertable-ai/duckdb-semantic_layer/actions/workflows/MainDistributionPipeline.yml/badge.svg)](https://github.com/altertable-ai/duckdb-semantic_layer/actions/workflows/MainDistributionPipeline.yml)
[![DuckDB](https://img.shields.io/badge/DuckDB-v1.5.5-fff100?logo=duckdb)](https://duckdb.org)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

**A semantic layer inside DuckDB.** Define your business metrics once, in SQL, next to your data. Then query any
combination of dimensions and metrics from SQL or from a BI tool, and get correct numbers every time.

Aggregating across joined tables is where analytics quietly goes wrong. Join orders to their line items and every
order total is counted once per line. Compute "revenue per customer" in two dashboards and the two rarely agree.
`semantic_layer` lets you describe your data once: logical tables, the relationships between them, and the facts,
dimensions and metrics that matter to the business. Every query then gets its joins and aggregations generated at the
right grain.

- **Define once, reuse everywhere.** Each metric has a single definition, shared by every query, notebook and
  dashboard.
- **Correct by construction.** Joins only follow many-to-one relationships, and metrics of different grains are
  aggregated separately. Queries that would fan out are rejected instead of returning inflated numbers.
- **As fast as hand-written SQL.** Semantic queries are expanded into ordinary DuckDB SQL at bind time, with no
  custom operator. On a 100M-row fact table they run within a few percent of the equivalent hand-written query (see
  [benchmarks](docs/benchmarks.md)).
- **Just SQL, no extra service.** Define views with `CREATE SEMANTIC VIEW` and query them with `SEMANTIC_VIEW(...)` or
  a plain `SELECT ... GROUP BY`, all inside DuckDB. There are no YAML files and no separate semantic-layer server.
- **Time intelligence built in.** One `TIME (<column>)` per table gives every metric a shared calendar
  (`metric_time.day` / `week` / `month` / `quarter` / `year`), with period-over-period offsets, running totals,
  to-date and trailing windows.
- **Real-world modeling.** Many-to-many relationships, semi-additive metrics (balances, inventory), role-playing
  relationships, time-dependent and range joins, metric filters and window metrics such as rolling averages.
- **Fast dashboards with materializations.** Pre-aggregate metrics at a chosen grain; matching queries read them
  transparently, and DuckLake sources are refreshed incrementally.
- **Works with your tools.** Semantic views appear in `information_schema` like regular views, with one typed column
  per dimension, fact and metric, so SQL clients and BI tools discover them.
- **Snowflake-compatible.** The syntax follows
  [Snowflake semantic views](https://docs.snowflake.com/en/user-guide/views-semantic/overview), so definitions and
  queries written for Snowflake run on DuckDB.

## Quick start

```sql
INSTALL semantic_layer FROM community;
LOAD semantic_layer;
```

The example uses the TPC-H tables generated by DuckDB's `tpch` extension.

```sql
INSTALL tpch;
LOAD tpch;
CALL dbgen(sf = 0.01);

CREATE SEMANTIC VIEW sales
  TABLES (
    orders    AS orders    PRIMARY KEY (o_orderkey) TIME (o_orderdate),
    customers AS customer  PRIMARY KEY (c_custkey),
    lines     AS lineitem  PRIMARY KEY (l_orderkey, l_linenumber)
  )
  RELATIONSHIPS (
    orders_to_customers AS orders (o_custkey) REFERENCES customers,
    lines_to_orders     AS lines (l_orderkey) REFERENCES orders
  )
  FACTS (
    lines.net_price   AS l_extendedprice * (1 - l_discount),
    orders.line_count AS COUNT(lines.l_linenumber)
  )
  DIMENSIONS (
    customers.segment AS c_mktsegment,
    orders.order_year AS YEAR(o_orderdate)
  )
  METRICS (
    lines.revenue        AS SUM(lines.net_price),
    lines.revenue_ly     OFFSET (metric_time.day BY INTERVAL 1 YEAR) AS lines.revenue,
    lines.revenue_ytd    CUMULATIVE (metric_time.day TO YEAR) AS SUM(lines.net_price),
    orders.avg_order     AS AVG(o_totalprice),
    orders.avg_lines     AS AVG(orders.line_count),
    customers.customers  AS COUNT(*),
    revenue_per_customer AS lines.revenue / customers.customers,
    revenue_growth       AS lines.revenue / lines.revenue_ly - 1
  )
  COMMENT = 'TPC-H sales';
```

Ask for dimensions and metrics. The extension joins `lineitem → orders → customer`, aggregates every metric at its
own grain and filters before aggregating:

```sql
SELECT * FROM SEMANTIC_VIEW(
  sales
  DIMENSIONS customers.segment, orders.order_year
  METRICS lines.revenue, orders.avg_order, orders.avg_lines
  WHERE orders.order_year >= 1998
)
ORDER BY segment, order_year;
```

```text
┌────────────┬────────────┬───────────────┬────────────────────┬────────────────────┐
│  segment   │ order_year │    revenue    │     avg_order      │     avg_lines      │
├────────────┼────────────┼───────────────┼────────────────────┼────────────────────┤
│ AUTOMOBILE │       1998 │ 31351135.6035 │ 137129.28886554623 │  3.907563025210084 │
│ BUILDING   │       1998 │ 42958542.7181 │ 138360.51198142415 │ 3.9226006191950464 │
│ ...        │        ... │           ... │                ... │                ... │
```

The same view can be queried by name, like a regular view, with metrics wrapped in `AGG(...)`:

```sql
SELECT segment, AGG(revenue) AS revenue
FROM sales
WHERE order_year = 1998
GROUP BY segment
ORDER BY revenue DESC;
```

Metrics of different tables combine safely: `revenue_per_customer` divides revenue (aggregated over line items) by
the number of customers (aggregated over customers) within each segment. A query that would break that guarantee is
rejected. For example, a customer count cannot be grouped by `orders.order_year`, because customers have no order
year:

```sql
SELECT * FROM SEMANTIC_VIEW(sales DIMENSIONS orders.order_year METRICS customers.customers);
-- Binder Error: Invalid dimension specified: The dimension entity 'orders' must be related to and have an equal or
-- lower level of granularity compared to the base metric or dimension entity 'customers'.
```

`TIME (o_orderdate)` gives the view a calendar, `metric_time`, that every metric reaching `orders` can be grouped by
(line items inherit their order's date). Month-by-month revenue, year to date, and growth over the same month of the
previous year:

```sql
SELECT * FROM SEMANTIC_VIEW(
  sales
  DIMENSIONS metric_time.month
  METRICS lines.revenue, lines.revenue_ytd, revenue_growth
  WHERE metric_time.year = DATE '1997-01-01'
)
ORDER BY month;
```

```text
┌────────────┬───────────────┬────────────────┬───────────────────────┐
│   month    │    revenue    │  revenue_ytd   │    revenue_growth     │
├────────────┼───────────────┼────────────────┼───────────────────────┤
│ 1997-01-01 │ 27189203.2127 │  27189203.2127 │   0.11652074680918045 │
│ 1997-02-01 │ 26202133.8903 │  53391337.1030 │   0.06044752749517368 │
│ 1997-03-01 │ 26951768.0447 │  80343105.1477 │ -0.004401808934953566 │
│ ...        │           ... │            ... │                   ... │
```

The `WHERE` selects 1997, yet `revenue_growth` still reads 1996 for its comparison: offsets and windows are part of
the metric, not of the query.

## Installation

The extension is distributed through the
[DuckDB community extensions](https://duckdb.org/community_extensions/) repository, for DuckDB **v1.5.5**:

```sql
INSTALL semantic_layer FROM community;
LOAD semantic_layer;
```

### Building from source

```bash
git clone --recurse-submodules https://github.com/altertable-ai/duckdb-semantic_layer.git
cd duckdb-semantic_layer
GEN=ninja make
```

The build produces:

- `./build/release/duckdb`, a DuckDB shell with the extension (and `tpch`) statically linked, ready to use;
- `./build/release/extension/semantic_layer/semantic_layer.duckdb_extension`, a loadable extension for DuckDB v1.5.5.

To load the extension into another DuckDB v1.5.5 client, allow unsigned extensions and load the file:

```bash
duckdb -unsigned
```

```sql
LOAD '/path/to/semantic_layer.duckdb_extension';
```

## Defining a semantic view

```sql
CREATE [ OR REPLACE | OR ALTER ] SEMANTIC VIEW [ IF NOT EXISTS ] <name>
  TABLES ( <logical table> [, ...] )
  [ RELATIONSHIPS ( <relationship> [, ...] ) ]
  [ FACTS ( <fact> [, ...] ) ]
  [ DIMENSIONS ( <dimension> [, ...] ) ]
  [ METRICS ( <metric> [, ...] ) ]
  [ COMMENT = '<text>' ]
```

The definition is validated when it is created: tables and columns must exist, keys and relationships must be
consistent, the relationship graph must be acyclic, expressions must type-check and follow the aggregation rules
below. Every member's data type is recorded.

### Logical tables

```sql
[ <alias> AS ] { <table or view> | ( <select query> ) }
  [ PRIMARY KEY ( <column> [, ...] ) ]
  [ UNIQUE ( <column> [, ...] ) ] [...]
  [ CONSTRAINT [ <name> ] DISTINCT RANGE BETWEEN <start column> AND <end column> EXCLUSIVE ]
  [ TIME ( <column> ) ]
  [ WITH SYNONYMS [ = ] ( '<synonym>' [, ...] ) ]
  [ COMMENT = '<text>' ]
```

A logical table is a table, a view or a parenthesized query. Its alias (by default the table name) is how the rest of
the definition refers to it. `TIME` declares the date or timestamp its rows are aggregated over (see
[time spine](#time-spine-time)).

### Relationships

```sql
[ <name> AS ] <table> ( <column> [, ...] ) REFERENCES <referenced table>
  [ ( { [ ASOF ] <column> [, ...] | BETWEEN <start column> AND <end column> EXCLUSIVE } ) ]
```

A relationship is a many-to-one (or one-to-one) foreign key. The referenced columns default to the referenced
table's primary key, or to its only unique key. Unnamed relationships get a generated name (`<from>_to_<to>`). See
[advanced modeling](#advanced-modeling) for `ASOF` and range relationships.

### Facts, dimensions and metrics

```sql
-- facts: row-level values (measures before aggregation)
[ PRIVATE | PUBLIC ] <table>.<fact> AS <expression> [ WITH SYNONYMS ( ... ) ] [ COMMENT = '<text>' ]

-- dimensions: row-level attributes to group and filter by
<table>.<dimension> AS <expression> [ WITH SYNONYMS ( ... ) ] [ COMMENT = '<text>' ]

-- metrics: aggregates
[ PRIVATE | PUBLIC ] [ <table>. ]<metric>
  [ USING ( <relationship> [, ...] ) ]
  [ NON ADDITIVE BY ( <dimension> [ ASC | DESC ] [ NULLS { FIRST | LAST } ] [, ...] ) ]
  [ FILTER ( WHERE <condition> ) ]
  [ OFFSET ( <dimension> BY <interval> ) ]
  [ CUMULATIVE ( <dimension> [ OVER <interval> | TO <date part> ] [ FIRST | LAST | AVERAGE ] ) ]
  AS <expression> [ WITH SYNONYMS ( ... ) ] [ COMMENT = '<text>' ]
```

- **Facts and dimensions** are row-level expressions of their table. They can use the table's columns and other
  facts and dimensions of the same table or of tables it references (many-to-one). They can also aggregate the rows of
  a table that references them (`orders.line_count AS COUNT(lines.l_linenumber)` counts the lines of each order).
- **Table metrics** (`<table>.<metric>`) aggregate the rows of their table: `SUM(lines.net_price)`, `COUNT(*)`.
  Aggregates may be nested to aggregate a finer table first (`customers.avg_orders AS AVG(SUM(orders.o_totalprice))`),
  and metrics may combine other metrics of the same or referenced tables.
- **Derived metrics** (no table prefix) combine metrics of different tables:
  `revenue_per_customer AS lines.revenue / customers.customers`.
- **`PRIVATE`** facts and metrics can be used in other definitions but not queried.
- Names are referenced as `<table>.<name>`, or by bare name when it is unique in the view.

## Querying

### The `SEMANTIC_VIEW` clause

```sql
SELECT ... FROM SEMANTIC_VIEW(
  <semantic view>
  [ DIMENSIONS <expression> [ [ AS ] <alias> ] [, ...] ]
  [ METRICS <expression> [ [ AS ] <alias> ] [, ...] ]
  [ FACTS <expression> [ [ AS ] <alias> ] [, ...] ]
  [ WHERE <condition> ]
) [ AS <alias> ]
```

- The result has one column per requested item, in clause order, named after the member (or its alias).
- `DIMENSIONS` items can be expressions over dimensions and facts (`YEAR(orders.order_date) AS year`). `METRICS` items
  can be expressions over metrics or ad-hoc aggregates (`COUNT(DISTINCT customers.segment)`). `<table>.*` selects every
  public member of that kind of a logical table.
- `WHERE` filters rows before aggregation. It may reference dimensions and facts (not metrics) and uncorrelated
  subqueries.
- `FACTS` returns row-level values (grouped by `DIMENSIONS` when both are given). `FACTS` and `METRICS` cannot be
  combined.
- `SEMANTIC_VIEW(...)` is a table expression: it can be joined, filtered, ordered, used in CTEs, `CREATE TABLE AS`,
  `INSERT ... SELECT`, views, `EXPLAIN` and prepared statements.

A dimension can be combined with a metric only if it lies on the metric's table or on a table the metric's table
references (the *equal or lower granularity* rule), or across a
[many-to-many bridge](#many-to-many-relationships-bridge-tables). Otherwise the query is rejected.

### Querying by name

```sql
SELECT customers.segment, AGG(lines.revenue), AGG(orders.avg_order) * 2 AS double_avg
FROM sales
WHERE orders.order_year >= 1995
GROUP BY customers.segment
HAVING AGG(lines.revenue) > 1000
ORDER BY 2 DESC;
```

In this form:

- `GROUP BY` expressions become dimensions.
- Metrics are wrapped in `AGG(...)`; other aggregate functions over dimensions or facts are ad-hoc metrics.
- `WHERE` filters before aggregation, `HAVING` after.
- Without aggregation, the select list is evaluated as facts, row by row.
- Names can be bare, qualified (`customers.segment`) or quoted as BI tools write them (`"customers.segment"`).
- Joins with the semantic view, window functions, `QUALIFY`, `SELECT *`, and multiple grouping sets (`ROLLUP`,
  `CUBE`, or `GROUPING SETS`) are not supported in this form. For subtotals, use `UNION ALL` of separately grouped
  semantic queries so each metric is evaluated at the appropriate grain.

### Seeing the generated SQL

```sql
SELECT sql FROM semantic_view_sql('SELECT * FROM SEMANTIC_VIEW(sales DIMENSIONS customers.segment METRICS lines.revenue)');
```

`semantic_view_sql` returns the statement with every semantic query expanded into the plain SQL DuckDB runs.

## Advanced modeling

### Role-playing relationships (`USING`)

When several relationships connect the same tables (a flight's departure and arrival airports), `USING` on a metric
chooses the path. Without it such queries are rejected as ambiguous.

```sql
RELATIONSHIPS (
  departure AS flights (departure_airport) REFERENCES airports,
  arrival   AS flights (arrival_airport)   REFERENCES airports
)
METRICS (
  flights.departures USING (departure) AS COUNT(*),
  flights.arrivals   USING (arrival)   AS COUNT(*)
)
```

### Many-to-many relationships (bridge tables)

A table with relationships to two tables bridges them:

```sql
TABLES (authors PRIMARY KEY (author_id), books PRIMARY KEY (book_id), book_authors PRIMARY KEY (book_id, author_id))
RELATIONSHIPS (book_authors (author_id) REFERENCES authors, book_authors (book_id) REFERENCES books)
```

`books.total_pages` can then be grouped or filtered by `authors.country`. Each book counts **once per group**: a book
with two French authors counts once for `FR`. Totals without bridged dimensions are unchanged. Any table with
relationships to both sides acts as a bridge, fact tables included: `customers.customer_count` by
`products.category` through `sales` counts the customers who bought in each category. A dimension stored on the
bridge itself is still rejected. When several bridges connect the same tables, `USING (<relationship>)` on the metric
picks one.

Rows without any bridge row (a book without authors) get NULL bridged dimensions. A `WHERE` condition on bridged
tables keeps only the rows with a matching bridge row.

### Semi-additive metrics (`NON ADDITIVE BY`)

```sql
METRICS (accounts.balance NON ADDITIVE BY (dates.day) AS SUM(balance))
```

Balances and inventory levels must not be summed over time. Within every group, a semi-additive metric only
aggregates the rows of the last snapshot in the given order.

### Metric filters (`FILTER`)

```sql
METRICS (
  invoices.revenue AS SUM(amount),
  costs.cost       AS SUM(cost),
  margin AS (invoices.revenue - costs.cost) / invoices.revenue,
  enterprise_margin FILTER (WHERE accounts.segment = 'enterprise') AS margin
)
```

A metric filter restricts the rows of every aggregate the metric is computed from, including the aggregates of the
metrics it references (here both the revenue and the cost). Filters of nested metrics combine with `AND`. The condition
is row-level (dimensions, facts and columns), and every table it reads must be reachable from the table of each
aggregate it applies to. A filtered metric is an ordinary aggregate with a `FILTER` clause, so it can be materialized.
For semi-additive metrics, the filter applies before the last snapshot is picked, like a query's `WHERE`.

### Time spine (`TIME`)

```sql
TABLES (
  invoices  PRIMARY KEY (invoice_id)  TIME (invoiced_at),
  shipments PRIMARY KEY (shipment_id) TIME (ordered_at)
)
RELATIONSHIPS (
  shipped AS shipments (shipped_at) REFERENCES metric_time
)
DIMENSIONS (
  metric_time.weekday AS dayofweek(day)
)
METRICS (
  invoices.revenue AS SUM(amount),
  invoices.revenue_ly OFFSET (metric_time.day BY INTERVAL 1 YEAR) AS revenue,
  shipments.booked AS SUM(booked),
  shipments.shipped_amount USING (shipped) AS SUM(booked)
)
```

`TIME (<column>)` on a logical table declares its aggregation time: a `DATE`, `TIMESTAMP` or `TIMESTAMPTZ` column.
The view then has a built-in logical table `metric_time` (its primary key is `day`) and the dimensions `day`, `week`,
`month`, `quarter` and `year`. `metric_time.day` is `CAST(<column> AS DATE)` (`TIMESTAMPTZ` is cast to `TIMESTAMP`
first, in the session time zone); the other grains are `DATE_TRUNC` of that day, cast back to `DATE` (weeks start on
Monday). Further dimensions, such as a fiscal quarter, can be defined on `metric_time` from `day`. Facts and metrics
cannot.

`metric_time` is never joined or scanned. A query reads the time column of the table that owns it, joining only up to
that table, so a line item inherits its invoice's time through an ordinary relationship. It is not a source for
freshness checks or incremental refresh, and a query that would read only the spine (no metric and no fact) is
rejected: the spine has no rows of its own. Days with no facts are absent from ordinary aggregates.

Each `TIME` is that table's default path to `metric_time`. Another date is an ordinary relationship
(`shipped AS shipments (shipped_at) REFERENCES metric_time`), chosen with `USING (shipped)`; without `USING`, `TIME`
wins. A table that reaches two different `TIME` columns and does not choose one is ambiguous, as any other
relationship is. The name `metric_time` is reserved only in a view that uses `TIME`.

### Time offsets (`OFFSET`)

```sql
METRICS (
  margin_ly OFFSET (metric_time.day BY INTERVAL 1 YEAR) AS margin,
  margin_growth AS (margin - margin_ly) / NULLIF(margin_ly, 0)
)
```

For a group dated *t*, an offset metric is computed from the rows dated *t − interval* (a negative interval looks
forward). The dimension must be defined as a column of its table (typically `metric_time.day`, from [`TIME`](#time-spine-time));
every dimension computed from that column moves with it, so the offset works at any grain (`metric_time.month`,
`metric_time.year`, ...), and a `WHERE` on time selects the previous period's rows. Only that column is shifted, so a
query with an offset metric must have a dimension or `WHERE` condition computed from it, and cannot read other columns
of a date table (a stored `d_year` would not move with the date: define `metric_time.year`, or `dates.year AS year(day)`,
instead). The metric's own definition (its aggregates and filters) reads the stored values. Offsets of nested metrics
add up. Offset metrics cannot be materialized (the other metrics of a query still read materializations) or referenced
by facts and dimensions.

### Cumulative metrics (`CUMULATIVE`)

```sql
METRICS (
  events.revenue_total CUMULATIVE (metric_time.day)                      AS SUM(amount),             -- running total
  events.revenue_mtd   CUMULATIVE (metric_time.day TO MONTH)             AS SUM(amount),             -- month to date
  events.wau           CUMULATIVE (metric_time.day OVER INTERVAL 7 DAYS) AS COUNT(DISTINCT user_id), -- trailing window
  events.wau_ly        OFFSET (metric_time.day BY INTERVAL 1 YEAR)       AS wau
)
```

For a group dated *t* (the *anchor*), a cumulative metric aggregates the rows dated up to *t*: all of them, those of
the last `OVER` interval (*t − interval < date ≤ t*), or those since the start of *t*'s `TO` period (`week`, `month`,
`quarter`, `year`, ...). It is computed from the rows themselves, so distinct counts are exact and days without data
do not shorten a window. As with `OFFSET`, the dimension must be defined as a column (typically `metric_time.day`),
dimensions and `WHERE` conditions computed from it read the anchor (`WHERE metric_time.day >= '2024-01-01'` selects
anchors whose windows still read 2023), and other columns of a date table cannot be read in the same query.

- Anchors are the dates of the dimension's table that have rows in their window, up to the latest date of the
  metric's rows (after the query's other `WHERE` conditions). A metric `FILTER` does not remove anchors: a filtered
  metric is 0 or NULL where its window only holds filtered-out rows.
- At a coarser grain (`metric_time.month`) or without a time dimension, the value is the one at each group's last anchor
  (`LAST`, the default: month-end month-to-date), its first anchor (`FIRST`), or the average over its anchors
  (`AVERAGE`, for metrics computed from a single aggregate). MetricFlow's `period_agg` defaults to `first`.
- In a derived cumulative metric over several tables, each table's anchors stop at its own latest row.
- `OFFSET` and `FILTER` can be applied to a cumulative metric. Not supported: cumulative metrics of metrics that use
  `OFFSET`, `CUMULATIVE` or `NON ADDITIVE BY`, window functions in a cumulative metric, and facts or dimensions that
  reference one. Cumulative metrics cannot be materialized (the other metrics of a query still read
  materializations).
- Decomposable aggregates (`SUM`, `COUNT`, `AVG`, `MIN`, `MAX`) and `DISTINCT` aggregates are pre-aggregated by date
  before the windows are joined; other aggregates (`MEDIAN`, ...) read every row once per anchor in its window.
  Anchors are the distinct values of the column: over a fine-grained column (a timestamp of a large fact table), a
  running total or to-date window joins each value to every later one, which grows quadratically. Use `metric_time.day`,
  or another day-grain dimension, for those windows. Over the built-in time spine, anchors are every day from the
  rows' earliest date to their latest, so a gap inside that range does not drop a running total.

### Time-dependent and range relationships

- `ASOF` relationships join each row to the latest referenced row at or before its value:
  `orders (o_cust_id, o_ord_date) REFERENCES addresses (ca_cust_id, ASOF ca_start_date)`.
- Range relationships look up the range that contains each value:
  `events (ts) REFERENCES periods (BETWEEN start_time AND end_time EXCLUSIVE)`, with
  `CONSTRAINT DISTINCT RANGE BETWEEN start_time AND end_time EXCLUSIVE` declared on `periods` (NULL bounds are open).
  The lookup runs on the distinct values of the referencing column, which is much cheaper than a range join.

### Window function metrics

```sql
METRICS (
  sales.avg_7_days AS AVG(sales.total_quantity) OVER (
    PARTITION BY EXCLUDING dates.day ORDER BY dates.day
    RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW
  )
)
```

Window function metrics are evaluated over the aggregated rows. The dimensions they use must be requested in the
query (`SHOW SEMANTIC DIMENSIONS IN <view> FOR METRIC <metric>` marks them as `required`).
`PARTITION BY EXCLUDING d` partitions by every requested dimension except `d`.

## Materializations

A materialization stores the aggregates of some metrics at a chosen grain. Queries that can be answered from it read
the stored aggregates instead of scanning the sources, transparently: nothing changes in how the semantic view is
queried.

```sql
ALTER SEMANTIC VIEW sales ADD MATERIALIZATION revenue_by_segment_year
  AS DIMENSIONS customers.segment, orders.order_year
     METRICS lines.revenue, orders.avg_order;

-- read from the materialization, rolled up from (segment, year) to segment
SELECT customers.segment, AGG(lines.revenue) FROM sales GROUP BY customers.segment;
```

```sql
ALTER SEMANTIC VIEW <view> ADD MATERIALIZATION [IF NOT EXISTS] <name>
  [REFRESH_MODE = AUTO | FULL | INCREMENTAL] [IN <database>[.<schema>]]
  AS DIMENSIONS <dimension> [, ...] METRICS <metric> [, ...]
ALTER SEMANTIC VIEW <view> REFRESH MATERIALIZATION <name> [AUTO | FULL | INCREMENTAL]
ALTER SEMANTIC VIEW <view> DROP MATERIALIZATION [IF EXISTS] <name>
ALTER SEMANTIC VIEW <view> SET MAX_STALENESS = <seconds> | UNSET MAX_STALENESS
SHOW SEMANTIC MATERIALIZATIONS [LIKE '<pattern>'] [IN <view>]
```

**What is stored.** One table per aggregation block (the metrics' aggregates over the same table), in the schema
`__semantic_materializations` of the semantic view's database, or of the database named by `IN` (any writable
DuckDB database, file or in-memory, or DuckLake catalog; `IN lake.analytics` also picks the schema). Each row is a
group of the materialization's dimensions and holds the *state* of every aggregate rather than its final value, so
that coarser queries and incremental refreshes stay exact: `SUM` stores a sum and a count, `AVG` a sum and a count,
`COUNT` a count, `MIN` / `MAX` the extreme value, plus the number of rows of the group. Other aggregates
(`COUNT(DISTINCT ...)`, `median`, ...) are stored as they are. Physical table names include a persisted allocation ID,
so identically named views in different schemas or databases have separate storage; renames keep the same tables.
Restoration rejects legacy allocations claimed by multiple owners and preserves their tables and metadata.

**When a query uses it.** A block of a query is read from a materialization when the materialization stores all of
its aggregates, the query's dimensions and `WHERE` clause can be computed from the stored dimensions (for example
`YEAR(orders.order_date)` from `orders.order_date`), and the materialization is fresh. Grouping by fewer dimensions
rolls the stored groups up (`SUM` of sums, sum of sums divided by sum of counts for `AVG`, ...); aggregates stored as
they are only answer queries at the materialization's own grain. When several materializations qualify, the one with
the fewest dimensions (the fewest groups to aggregate) is read. Derived metrics combine blocks read from
materializations and blocks computed from the sources. `semantic_view_sql()` shows which tables a query reads, and
`SET semantic_view_materializations = false` disables them.

**Freshness.** Materializations of DuckLake tables record the snapshot they were built at; a query uses one only if
none of its sources changed since (or within `MAX_STALENESS`, see below). DuckDB tables have no change tracking, so a
materialization over them is used only when the semantic view sets `MAX_STALENESS` (seconds since its last refresh);
otherwise queries read the sources. SQL subqueries can read sources outside the semantic model, and user-defined SQL
macros can be replaced without changing any source snapshot. Materializations using either have unknown freshness
and require `MAX_STALENESS` to be read. Prepared statements check freshness again at every execution.
`SHOW SEMANTIC MATERIALIZATIONS` tells whether each materialization is usable and why not.

**Refresh.** `REFRESH MATERIALIZATION` brings a materialization up to date in its own transaction, using its
`REFRESH_MODE` unless another mode is given:

- `FULL` rebuilds it from the sources (read at one consistent snapshot).
- `INCREMENTAL` applies the changes since the last refresh, and fails (explaining why) when that is not possible.
- `AUTO` (the default) refreshes incrementally when possible and rebuilds otherwise; `SHOW SEMANTIC MATERIALIZATIONS`
  reports what the last refresh did and why.

Incremental refresh needs every source to be a DuckLake table. It finds the changed tables in the snapshots'
metadata, reads their inserted and deleted rows since the last refresh (`ducklake_table_insertions()` /
`ducklake_table_deletions()`), and works on those rows and the groups they touch:

- changed rows of a metric's table (inserts, deletes, updates, also of foreign keys) are removed with their old
  values and dimensions and added back with the new ones;
- changed rows of a table its dimensions come from (a customer changing segment) move the unchanged rows that
  reference them from their old group to their new one. Finding those rows scans the metric's table twice (as of
  before and as of now), so `AUTO` rebuilds such blocks instead, which scans it once;
- changed rows of a table aggregated by a nested aggregation (`FACTS (customers.order_total AS
  SUM(orders.amount))` aggregated again by `AVG(customers.order_total)`) recompute, as of before and as of now, the
  rows whose nested aggregation reads them; here too `AUTO` rebuilds the block instead;
- `SUM`, `COUNT` and `AVG` states are updated arithmetically; groups whose row count drops to zero disappear;
- `MIN` / `MAX` merge new rows directly, and groups that lost rows are recomputed from the sources, like every
  affected group of an aggregate stored as is.

A refresh falls back to a full rebuild (or fails in `INCREMENTAL` mode) when a source is not a DuckLake table, a
dimension aggregates other rows, a metric uses a subquery, a replaceable SQL macro, or a nested aggregation of anything but the columns of a
table directly referencing a table of the materialization, a join uses an `ASOF` or range relationship, the change
history since the last refresh was expired, the definition of a source table changed (altered, dropped or
re-created: changes to other tables do not matter), or the materialization's table is missing. Without source
changes, a refresh does nothing. A failed refresh leaves the materialization as it was. Inserts cost about the number of new rows; deletes
and updates also read the deleted rows' old values from DuckLake's data files. See
[docs/benchmarks.md](docs/benchmarks.md#materialization-refresh) for measurements on 100M rows.

**Persistence.** Next to its tables, each storage schema `__semantic_materializations` holds a table
`__sv_materializations` recording every materialization stored in that database: its definition, tables, the
snapshots it was built at and its last refresh, updated in the refresh's transaction. Semantic views live in memory,
but their materializations survive restarts: re-creating the view (`CREATE`, `CREATE OR REPLACE`) brings back the
materializations stored for it in every attached database, reattached to their tables. One whose aggregates changed
with the new definition is rebuilt by its next refresh; one the new definition can no longer serve is dropped. Adding
a materialization that is already stored with the same definition reattaches it too. `DROP SEMANTIC VIEW` and
`DROP MATERIALIZATION` drop the tables and their records; renaming the view keeps them. A DuckLake catalog attached
under another name is found again (materializations stored in in-memory databases are gone with them).

Valid materializations can be reattached from read-only storage; adding, refreshing, dropping or renaming them
requires writable storage. DDL stages its storage changes before publishing the new semantic view, so a failed
build or storage update leaves the registered view intact. Tables and metadata change together in each storage
database. Changes spanning multiple databases prepare all operations before committing each database separately.

Materializations cannot include semi-additive metrics, offset metrics (`OFFSET`), cumulative metrics (`CUMULATIVE`)
or dimensions reached through a many-to-many bridge.

## Managing and inspecting semantic views

| Statement | Description |
|---|---|
| `DROP SEMANTIC VIEW [IF EXISTS] <name>` | |
| `ALTER SEMANTIC VIEW [IF EXISTS] <name> RENAME TO <new name>` | |
| `ALTER SEMANTIC VIEW [IF EXISTS] <name> SET COMMENT = '<text>' \| UNSET COMMENT` | |
| `DESCRIBE SEMANTIC VIEW <name>` | the definition, one property per row (`object_kind, object_name, parent_entity, property, property_value`) |
| `SHOW SEMANTIC VIEWS [LIKE '<pattern>'] [IN SCHEMA <schema> \| IN DATABASE <database>]` | |
| `SHOW SEMANTIC DIMENSIONS \| FACTS \| METRICS [LIKE '<pattern>'] [IN <name>]` | defined members (including private ones), with their data types |
| `SHOW SEMANTIC DIMENSIONS [LIKE '<pattern>'] IN <name> FOR METRIC <metric>` | the dimensions a metric can be grouped by |
| `SHOW SEMANTIC MATERIALIZATIONS [LIKE '<pattern>'] [IN <name>]` | materializations, their tables, last refresh and whether queries can use them ([materializations](#materializations)) |

Every statement can be used as a table expression: `SELECT name FROM (SHOW SEMANTIC METRICS IN sales)`.

## BI tools and the catalog

Every semantic view is also listed as a view of the same name in `information_schema.tables` and `.columns`,
`duckdb_views()` and `duckdb_columns()`. SQL clients and BI tools therefore discover it like any other view:

- one column per public fact, dimension and metric (in that order), with the member's type and comment;
- a name shared by several members is qualified (`"orders.revenue"`), which the query-by-name form resolves;
- `DESCRIBE <name>` shows the same columns.

The catalog view is a placeholder, tagged `semantic_view` (see `duckdb_views().tags`). Reading it as a plain table
fails with a message pointing to `SEMANTIC_VIEW(...)` and `AGG(...)`. Semantic views therefore share the namespace of
tables and views: a semantic view cannot have the name of an existing table or view, and vice versa.

## How it works

A semantic query is expanded at bind time into an ordinary DuckDB query. There is no custom operator, so DuckDB's
optimizer, parallel hash joins and aggregates apply unchanged.

1. Every metric is decomposed into **aggregate atoms** (`SUM(amount)`, `COUNT(*)`, ...), each with a **home table**:
   the logical table whose rows it aggregates.
2. Atoms with the same home table form a **block**:
   `SELECT dims, aggregates FROM home LEFT JOIN <referenced tables> WHERE filter GROUP BY dims`. Joins only follow
   relationships towards the "one" side, so they can never multiply the home table's rows, and only the tables the
   query needs are joined.
3. Dimensions and filters reached through a **many-to-many bridge** come from a `SELECT DISTINCT (key, dimensions)`
   subquery over the bridge, joined on the key it shares with the home table. Each home row joins at most once per
   group of dimension values.
4. Blocks are merged on the dimension values (`UNION ALL` + `GROUP BY`, NULLs match), and derived metrics are computed
   on the merged rows.
5. Semi-additive metrics keep the last snapshot of every group before aggregating. Window function metrics run last,
   over the merged rows.
6. Facts and dimensions that aggregate finer rows, and nested aggregates, become correlated scalar subqueries, which
   DuckDB decorrelates into a hash aggregate and a join.

On a 100M-row fact table, the generated queries run within a few percent of equivalent hand-written SQL, and range
relationships are about 9x faster than a hand-written range join. See [docs/benchmarks.md](docs/benchmarks.md).

## Limitations

- **Definitions live in memory**, per database instance. They are not saved in the database file and must be
  re-created after a restart (their [materializations](#materializations) are saved, and come back with them). They are not transactional: a `CREATE` inside a rolled-back transaction stays.
- The **catalog placeholder views**, however, are saved in database files like any view. After a restart a
  placeholder stays listed, and querying it fails with `Semantic view "x" is not defined in this session`.
  `CREATE SEMANTIC VIEW x` replaces it and `DROP SEMANTIC VIEW x` removes it. Without the extension loaded, querying it
  fails with an unknown `__semantic_view_placeholder` function.
- No placeholder is created in read-only databases or in attached non-DuckDB catalogs (Postgres, SQLite, ...). Such
  semantic views work but are not listed. A plain `DROP VIEW x` removes only the placeholder.
- A DuckDB view cannot be defined over the query-by-name form; use `SEMANTIC_VIEW(...)` in view definitions.
- One statement cannot combine `SEMANTIC_VIEW(...)` with the syntax of another parser extension, such as
  `MATCH_RECOGNIZE`.

## Snowflake compatibility

The syntax and semantics follow
[Snowflake semantic views](https://docs.snowflake.com/en/user-guide/views-semantic/overview)
([CREATE SEMANTIC VIEW](https://docs.snowflake.com/en/sql-reference/sql/create-semantic-view),
[querying](https://docs.snowflake.com/en/user-guide/views-semantic/querying),
[validation rules](https://docs.snowflake.com/en/user-guide/views-semantic/validation-rules)), so definitions and
queries written for Snowflake run on DuckDB.

**Accepted and kept as metadata** (shown by `DESCRIBE SEMANTIC VIEW`, otherwise ignored), so that Snowflake
definitions can be pasted as is: `WITH SYNONYMS`, `LABELS = (FILTER)`, `SAMPLE_VALUES`, `IS_ENUM`, `WITH CORTEX SEARCH
SERVICE`, `AI_SQL_GENERATION`, `AI_QUESTION_CATEGORIZATION`, `AI_VERIFIED_QUERIES`, `[WITH] TAG`, `COPY GRANTS`, and the
`WAREHOUSE` of a materialization.

**Not supported:**

- `GET_DDL` and YAML import/export;
- window functions in fact and dimension definitions;
- the `INFORMATION_SCHEMA.SEMANTIC_*` views (semantic views appear in the regular catalog instead, see above);
- `SHOW ... TERSE / STARTS WITH / LIMIT`, and `ALTER ... SET TAG`;
- materialization filters (`WHERE`, `IMMUTABLE WHERE`), `SUSPEND` / `RESUME MATERIALIZATION` and automatic
  background refreshes: materializations are refreshed with `REFRESH MATERIALIZATION`;
- privileges (DuckDB has none).

**Differences:**

- `CREATE OR ALTER` behaves like `CREATE OR REPLACE` (materializations the new definition can still serve are
  kept).
- `MAX_STALENESS` is a number of seconds. Materializations of DuckDB tables, whose changes cannot be tracked, are only
  read within it.
- `REFRESH MATERIALIZATION` accepts an explicit `AUTO`, `FULL` or `INCREMENTAL` mode, and `ADD MATERIALIZATION` a
  storage database (`IN`).
- Expressions may reference physical columns of other logical tables directly (Snowflake requires a fact).
- Metric `FILTER (WHERE ...)`, `OFFSET (<dimension> BY <interval>)` and `CUMULATIVE (...)` clauses, and the built-in
  time spine (`TIME (<column>)`, logical table `metric_time`) are extensions, modeled on
  [dbt MetricFlow](https://docs.getdbt.com/docs/build/about-metricflow)'s time spine, cumulative metrics and offsets;
  adjacent string literals in DDL are concatenated.
